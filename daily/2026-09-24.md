## КАРТА ОДНОГО ЗАПРОСА (end-to-end)

1. Приём. Мост scripts/poller/main.ts + inbox.ts: апдейт копится в collector, пишется в data/telegram-inbox.json и data/telegram-queue.json ДО доставки. Offset — data/telegram-offset.json (offset + delivered update_id), ack только после подтверждения eve.
2. Доставка в eve. scripts/poller/deliver.ts, ошибки классифицирует scripts/lib/deliver-policy.ts (retry/config/bounded по HTTP-кодам). Вeve — durable-execution: workflow runtime пишет run/steps/events файлами в .eve/.workflow-data (сейчас 907 МБ, 10k+ событий, 2.3k шагов). Реально работает re-enqueue: «Re-enqueued N active run(s) on startup» (node_modules/eve/.../dist-D5bR13zs.js). Это и есть Run Ledger — чужой код, но уже есть и включён.
3. Inbound-пайплайн. agent/lib/telegram-inbound.ts: allowlist, транскрипция, медиа; реплика пишется в vault/daily (appendDaily) до ответа.
4. Routing/модель. agent/lib/model-provider.ts + provider.ts: MODEL_PROVIDER выбирается РАЗ при старте, fail-closed; fallback-цепочки на ходу нет (кроме write-pool в scripts/iva-write.py: gemini→terra→luna→routerai с журналом data/write-pool-usage.jsonl).
5. Ход модели. agent/hooks/trace.ts — журнал data/trace/YYYY-MM-DD.jsonl (каждый шаг, тул, терминальный исход; ключ хода tg:chat:message + sessionId/turnId). agent/hooks/usage.ts — data/usage.jsonl (токены по sessionId/turnId/step). Идентификаторы запроса: update_id (мост), chatKey, sessionId+turnId (внутри сессии turnId — счётчик, «turn_0» не уникален), runId workflow.
6. Side effects. bash-тул (agent/tools/bash.ts) — host-доступ, до exec проверяют self-restart-guard и destructive-guard; write_file/write_card/web — без ledger. Исходящие в Telegram — только через Outbox (agent/lib/outbox.ts) + локальная правка telegram-send-once.ts: идемпотентность ответа (claim по sessionId+turnId, claim ДО Bot API, release при нулевой доставке).
7. Финал. run-status.d (жной ход, пульс, отмена), turn.completed → Outbox → Bot API. Crash после «успех»-ответа до записи результата: reopen run из ledger.

## P0 GAP TABLE

trace_id:
- Уже есть: журнал хода data/trace (ADR-0010), ключ апдейта tg:chat:message, сквозные sessionId/turnId в trace + usage.
- Gap: нет сквозного короткого ID, который клеится к внешним действиям (cron-скрипты, bash-команды, посты), и нет единого запроса «вся история хода одним ключом».
- Minimal: не новый механизм, а консистентность — в trace-событие записывать один тот же trace_id во всех швах (уже почти так; добить cron-скрипты).
- Why: ответ на «что произошло» по одному ключу, не сопоставляя три журнала.

Run Ledger:
- Уже есть: durable workflow ledger eve (.eve/.workflow-data, runs/steps/events, re-enqueue на старте), telegram-queue/inbox файлы, write-pool-usage.jsonl, vault/daily.
- Gap: разрозненность. run-status.d / send-once.d / inbox / queue — JSON-файлы, не ledger, у них нет шагов и статусов; «что реально сделано» собирается вручную по журналу.
- Minimal: не строить новый, а вылечить старый: добавить steps в существующий workflow-ledger и читать его; SQLite не нужен, пока файл-лидger держит нагрузку.
- Why: «правда о том, что сделано» уже 90% существует, но разбросана.

Idempotent side effects:
- Уже есть: telegram-send-once (ответ), claimTelegramSend ДО Bot API, destructive-guard/self-restart-guard, fail-open, fs-atomic, provenance, iva-dup-check, archive-схема хранилищ.
- Gap: НЕ идемпотентны: bash с побочкой, write_file в vault/data, web-посты через CLI, гит-операции, cron-скрипты.
- Minimal: расширить паттерн claimTelegramSend на write-инструменты (claim до действия, ключ = tool+input_hash), переиспользуя telegram-send-once почти как есть.
- Why: повтор после crash/restart уже случался (тройные ответы), у bash/CLI-постов та же уязвимость.

Failure classification:
- Уже есть: deliver-policy.ts (retry/config/bounded), error-humanizer, provider fail-open, write-pool retry-цепочка, iva-retry-stats, self-restart/destructive guards, трассировка ошибок в trace.
- Gap: нет единой FailurePolicy для тулов (bash/write_file/cron-скрипты) — у каждого своя реакция, часто «проглотить в консоль». «Uncertain» (сделалось/не сделалось) не различается.
- Minimal: единый модуль классификации (по образцу deliver-policy), покрывающий тула: RATE_LIMIT/TIMEOUT/AUTH/TOOL_BAD_INPUT/TOOL_UNCERTAIN/LOCAL_INFRA; для bash — анализ exit code + кодов (уже есть errorCode в bash-туле).
- Why: «повторять ли действие» должно решаться одинаково везде, а не per-тул.

- Не дублировать send-once — он хорош, его надо обобщить, а не копировать.
