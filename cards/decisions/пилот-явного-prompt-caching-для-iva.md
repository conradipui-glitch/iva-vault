# Пилот явного prompt caching для IVA

## Решение
1 августа 2026 владелец подтвердил, что к теме надо вернуться через 2–3 дня. До следующего шага код и конфигурация не меняются.

## Текущее состояние
- IVA использует Codex/OpenAI Responses API с `store: false`; полный контекст реплеится со стороны IVA.
- Учёт usage уже содержит `cacheRead`/`cacheWrite`; на момент анализа кэш-чтения фактически работали.
- Vault заполняется append-only, ежедневный memory rollup идёт пакетно в 04:00 Asia/Omsk — это не надо заменять prompt cache.

## Следующий безопасный шаг
Измерительный этап 2–3 дня: разделить метрики по типу вызова (чат, tool-loop, planner, rollup), затем на одном контролируемом сценарии проверить явный стабильный префикс, `prompt_cache_key` и explicit breakpoint для GPT-5.6. Оценивать отдельно качество, безопасность, задержку, cache-hit и стоимость. Менять по одному параметру.

## Ограничения
Prompt cache — краткоживущий кэш точного префикса, а не долговременная память. Динамические данные, внешнее содержимое, дата/время, пользовательский ввод и tool-results нельзя смешивать со стабильным префиксом. Для применения правок потребуются build и перезапуск, который запускает владелец.


## Результат измерительного этапа (2026-08-03)

Замер по `data/usage.jsonl`, только вызовы `routerai` (472 шага модели, 52 хода):

| Срез | Попадание в кеш |
|---|---|
| `channel:telegram` | 47.7% |
| фоновые задачи (`http`) | 45.1% |
| шаг 0 (начало хода) | 9.1% по токенам |
| шаги 1–2 | 49.7% |
| шаги 3+ | 49.8% |

Ключевое: **префикс находится в кеше у 51 хода из 52 (98%)**. Низкие 9.1% на шаге 0 —
это доля токенов, а не доля ходов: в начале хода кешируется системная часть, а свежий
пользовательский ввод по определению новый.

Суммарная переплата за все промахи на первом шаге за период — **1.17**.

## Вывод: пилот не нужен, гипотеза не подтвердилась

Исходный план исходил из того, что префикс нестабилен и его надо закреплять явными
границами и `prompt_cache_key`. Замер это опровергает: кеш и так находится почти всегда,
и выигрывать там нечего — потолок ~48% создаётся не промахами, а тем, что на каждом шаге
tool-loop к неизменному префиксу дописываются свежие результаты инструментов. Они новые
по определению и закешированы быть не могут.

Плюс изменились условия: карточка писалась под Codex/Responses API со `store:false`,
а с 1 августа провайдер — RouterAI с DeepSeek, где префиксный кеш работает автоматически
и явных маркеров не требует.

**Реальный драйвер стоимости — не промахи кеша, а объём: 7.6 шагов модели на ход, и на
каждом заново прогоняется вся история.** Поэтому рычаг — размер окна, а не кеш.
Сделано 3 августа: `ROUTERAI_CONTEXT_WINDOW` снижен со 100000 до 48000
(сначала до 32000, но на нём владелец отметил потерю нити в длинных диалогах).

Статус: закрыто без внедрения. Возвращаться только если попадание в кеш просядет
заметно ниже 45% — это будет означать, что префикс действительно поехал.
