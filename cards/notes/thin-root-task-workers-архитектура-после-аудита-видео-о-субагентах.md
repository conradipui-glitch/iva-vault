# thin-root-task-workers-архитектура-после-аудита-видео-о-субагентах

23.08.2026 разобран ролик про оркестрацию субагентов (нашлись готовые YouTube-субтитры, 7297 слов; платное распознавание не запускалось, транскрипт сохранён в data/transcripts/gNsjZvzdGEE.txt, полный отчёт в data/custom/factory/reports/f1787486114890.md). confidence: EXTRACTED.

Главный вывод для Iva: не нужна «армия из 250 агентов». Лучшее решение — тонкий координатор → фиксированный workflow → 0–4 узких исполнителя → компактные структурированные результаты → проверка → финальное действие. Субагенты оправданы только когда работу можно независимо разделить; всё повторяемое превращать в обычный код и точечные LLM-вызовы.

Тезисы автора: субагенты для независимых частей (источники новостей, главы документа, модули, фрагменты исследования); главный агент не должен получать всё сырьё — ему нужны короткие карточки результата; для повторяемых процессов — фиксированный workflow; у каждого исполнителя контракт (вход, формат результата, разрешённые инструменты, дочерние агенты, бюджет, таймаут, критерий готовности); стабильные операции (дедупликацию, сортировку, проверку полей, форматирование, маршрутизацию) переносить в код; отдельный проверяющий — только где ошибка дорогая (публикация, код, память, данные).

Что НЕ переносить: сотни агентов ради эффектности; свободное рекурсивное создание подчинённых; API-ключи внутри промптов; shell и ФС каждому агенту; Telegram как внутреннюю память/message bus; отдельного verifier для мелких задач; попытку просто удалить системный промпт. «Оставить только терминал» — это НЕ минимальные привилегии, терминал слишком широк.

Предложенные узкие declared работники (по сути детализация этапа 3/7 оптимизации): background-digest-worker (утренний дайджест и фоновые отчёты), memory-recall-worker (вопрос+область → компактный evidence bundle), host-inspect-worker (read-only диагностика сервера), research-map-worker (2–4 независимых исследователя + один синтезатор). Плюс batch-inspect tool — один bounded tool вместо цепочек glob→grep→read_file→stat→bash. Каждый worker: короткий промпт, минимальные tools, структурированный output, запрет рекурсивного fan-out, собственный токен-бюджет, таймаут, максимум одна попытка.

Процент экономии обещать нельзя — нужен A/B на одинаковых задачах и одной модели. Главный резерв — число model-шагов и тяжёлый root-контекст, а не дополнительный prompt caching (кэш уже даёт ~58% cacheRead от input).
